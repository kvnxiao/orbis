# Development workflow

Orbis keeps each kind of record on one surface. The repository stores current state: package SPECs
define approved behavior, and instruction files define how agents work.
[GitHub Issues](https://github.com/kvnxiao/orbis/issues) and the
[Orbis Project](https://github.com/users/kvnxiao/projects/1) hold plans and progress records, and
the [wiki](https://github.com/kvnxiao/orbis/wiki) stores repository-wide decision records. Coding
agents do most of the work under instructions in this repository.

This page explains, for human contributors, how to ask for work and where each instruction lives.
Agents do not read it: they start at [`AGENTS.md`](../AGENTS.md) and follow its links.

## Roles

- The **developer** approves designs, authorizes work, resolves material decisions, and merges PRs.
  To **approve** a document, such as the complete design, a SPEC, or a plan's Design section, is to
  confirm it as final and ready for work. To **authorize** work is to set a request's scope and
  permit its implementation or other execution to begin. Approval does not authorize execution.
- The **orchestrator** is the main agent session. It owns decisions, coordination, verification, and
  delivery.
- A **delegate** is an agent that the orchestrator starts for bounded work and that reports back to
  it: `orbis-implementer` edits code and tests, `orbis-reviewer` and `orbis-conformance-reviewer`
  review read-only, and a documentation delegate edits documentation.

## Ask for work

In a new Codex or Claude Code session in the updated, trusted repository, send a request such as:

```text
Resume #<number>
```

The same entry point resumes a PR (`Resume PR #<number>`) or takes a direct request that does not
name an issue or PR, such as a package fix or a documentation update. The request does not need a
skill name.

- To limit the work, add a scope limit, such as `Resume #<number>, planning only`.
- To inspect without execution, ask `What is the status of #<number>?`.
- To name a skill, invoke `$<skill>` in Codex, `/skill:<skill>` in Pi, or `/<skill>` in Claude Code,
  such as `/specify-package`. The request still starts in `work-issue`, which routes it to the named
  skill. When a host does not discover the repository's `.agents/skills`, ask it to read the skill's
  `SKILL.md` directly.

A change to package behavior gets an issue; a fix within an approved contract, a documentation
change, or a tooling change goes straight to a PR. The orchestrator settles open decisions with you
through the global `brainstorm` skill and waits for your approval of the complete design before
editing. Agents never merge, push to the default branch, publish packages, create releases, or write
to repositories other than `kvnxiao/orbis`.

## How the instructions are organized

The instructions form a tree, and links point only down it. Each file is read at the step that uses
it, not up front.

```text
docs/development-workflow.md       this page; human overview; no agent reads it
AGENTS.md                          loaded by every agent session, including delegates
├─ .agents/skills/<skill>/         procedures
│  ├─ SKILL.md
│  └─ references/                  files that only this skill uses
├─ .agents/shared/                 agent-only rules that several skills or agents use
├─ docs/specifications.md          content standards that humans also apply
├─ docs/readme-guidelines.md
└─ .claude/agents/, .codex/agents/ delegate definitions
```

- `work-issue` handles every development request and is the only skill that starts another
  repository skill. It routes work to the specialist skills:
  - `specify-package` writes and amends SPECs.
  - `plan-implementation` writes issue plans.
  - `verify-conformance` checks an implementation against its SPEC.
  - `write-readme` writes READMEs.
  - `update-toolchain` refreshes dependencies.
- The shared files cover authorization, delegation, review, GitHub records, issues and labels,
  package conventions, instruction files, and Effect adoption.
- `pi-coding-agent-rules` and the matching `.claude/rules/` file are generated by `ruleskill` and
  are not edited in this repository. The global skills `review-changes`, `update-docs`,
  `audit-prose`, and `brainstorm` are installed outside the repository.
- Research behind package contracts lives in `packages/<name>/docs/research/`, and research behind
  repository standards lives in `docs/research/`.
- Each delegate definition sets its model and reasoning effort. The main session's model comes from
  [`.claude/settings.json`](../.claude/settings.json) and
  [`.codex/config.toml`](../.codex/config.toml), and both hosts' hooks route GitHub CLI calls
  through `agent-gh`. Host configuration changes apply to new sessions.
