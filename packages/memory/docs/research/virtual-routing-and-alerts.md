# Virtual routing, observer dispatch, and degradation alerts

Pi 1.1.0 does not expose a complete virtual-model target set or enforce its advertised limits as a capacity bound across routes. It does expose a useful boundary for a package's own helper calls: `ctx.modelRegistry.streamSimple(model, context, { onPayload(payload, model) })` invokes a conforming provider's callback with the resolved physical request model before sending its payload. That callback supports destination and capacity checks, but it does not supply a universal account identity or freeze all provider behavior. Preserve legitimate route changes within an explicitly authorized policy; require a cooperating integration or concrete provider configuration where account and endpoint identity cannot otherwise be established. TUI and RPC support nonmodal notifications; print and JSON need stderr diagnostics because their extension UI methods are no-ops.

## Decision informed

The observer is an auxiliary model that proposes updates to a continuation snapshot of obligations and relevant context. A file-inventory supplement adds cumulative file paths to the main agent's request when it uses a native checkpoint.

A background observer must send conversation evidence only to authorized destinations and must stop or reduce work when its request cannot be prepared within a supported model's capacity. The acting model's file-inventory supplement has a separate problem: its context handler must estimate the capacity of an upcoming acting request whose virtual route is not exposed there. This investigation distinguishes these two boundaries.

## Virtual targets and capacity bounds

**Observed in Pi 1.1.0 source and installed declarations:** `VirtualModelDefinition` has an arbitrary synchronous or asynchronous `route(request)` function. It has no declared targets, complete-route enumeration method, minimum capacity, or policy generation. The callback receives messages, selected thinking level, reason, previous response, failed response, optional branch state, and cancellation. Its result names a physical model and thinking level. Pi checks that the returned model is a current physical catalog model with configured credentials. It does not restrict the result to a declared subset. [Virtual-model types](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/virtual-models.ts), [runtime resolution](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/model-runtime.ts).

**Observed in Pi 1.1.0 source:** The virtual definition's optional `contextWindow` and `maxTokens` describe limits shown before a physical response exists. They are not validated against every possible route. The host subsequently uses the most recent physical response for displayed context usage and checks the newly routed model separately when preparing an acting request. A virtual model's registration can be replaced under the same provider and model ID. A router can also vary because of closure state, external data, or asynchronous work without changing its registration. [Virtual-model documentation](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/docs/virtual-models.md).

**Observed in Pi 1.1.0 runtime:** A single registered router advertised a 100,000-token window and alternated between physical models with windows of 10,000 and 1,000. `modelRegistry.getAll()` returned identical catalog data before and after those different routes. No registration change was required. This disproves treating virtual metadata or catalog equality as evidence of a fixed current route.

**Observed in Pi 1.1.0 source:** `getAll()`, `getAvailable()`, and `find()` expose current catalog or availability data. A complete current physical catalog is a possible superset at that instant, but it is not a declaration of the router's possible targets across time. Registrations and dynamic catalogs can change while asynchronous routing runs. Pi has private generations for model-catalog refresh publication; these do not expose a routing, credential, or authorization generation. Provider registration inspection methods do not inspect arbitrary route closures. [Registry API](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/model-registry.ts), [catalog refresh generations](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/src/models.ts).

The declarative OpenRouter and Vercel routing fields in model configuration control gateway behavior. They do not enumerate Pi virtual-model outputs or establish a capacity guarantee for an arbitrary callback. A trustworthy cross-route bound therefore needs an independently enforced allowed-target policy, complete metadata for that policy, and validation that each dispatched model belongs to it. Taking the minimum window across a catalog snapshot is insufficient without those additional guarantees.

## Exact public API map

| API                                                                       | Accessible information or control                                                                                            | Limit                                                                                                                                                                                                      |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.modelRegistry.streamSimple(model, context, options)`                 | Runs physical or virtual helper requests with request-time authentication; `.result()` returns the final assistant message   | Direct helper requests route with reason `direct`; they do not inherit the main agent's previous/failed response, retry reason, or branch routing state.                                                   |
| Per-call `options.onPayload(payload, model)`                              | Receives the provider payload and resolved physical model, including its model metadata and effective auth base-URL override | Does not receive the complete credential, environment, headers, or a canonical account ID. Payload and endpoint interpretation remain provider-specific.                                                   |
| Per-call `options.transformHeaders(headers)`                              | Receives merged model/auth/request headers before provider dispatch; rejection stops dispatch                                | Receives headers only, not the resolved model, API key, or environment.                                                                                                                                    |
| `ctx.modelRegistry.getApiKeyAndHeaders(physicalModel)`                    | Resolves API key, headers, optional base URL, and environment                                                                | Separate resolution is not an atomic authorization token for a later registry call; it can refresh credentials and exposes secret material that must remain private.                                       |
| `ctx.modelRegistry.getProvider(providerId)`                               | Returns a public provider object whose `streamSimple(model, context, options)` accepts explicit request options              | Direct invocation requires the caller to supply the required auth and provider policy; arbitrary provider behavior still requires trust.                                                                   |
| Exported SDK `ModelRuntime.resolveModel(model, messages, options)`        | Resolves a route before an SDK-owned dispatch                                                                                | `ExtensionContext` exposes `ModelRegistry`, not the host's `ModelRuntime`; the registry does not forward `resolveModel()`. Creating another runtime does not reproduce the host's extension registrations. |
| `pi.on('before_provider_request', ...)`                                   | Can replace an untyped payload                                                                                               | Event lacks the resolved model; runner catches thrown errors and continues. It is not a fail-closed denial interface.                                                                                      |
| `pi.on('before_provider_headers', ...)`                                   | Can mutate headers                                                                                                           | Event lacks resolved model/account; runner catches thrown errors and continues.                                                                                                                            |
| `model_select`, assistant messages, `onResponse`, `provider_stream_event` | Report selection or response identity                                                                                        | Selection is not physical dispatch; response observations happen after the request was sent.                                                                                                               |

**Observed in Pi 1.1.0 source and installed declarations:** The map above follows `ModelRegistry`, public `ModelRuntime`, `ModelsSimpleStreamOptions`, `ProviderRequestOptions`, and extension event declarations. No public resolved-model event or callback in these contracts supplies an authorization object that binds a validated account and policy to the later dispatch. [Registry](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/model-registry.ts), [request options](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/src/types.ts), [header transform](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/src/models.ts), [extension event dispatch](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/extensions/runner.ts), [package exports](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/index.ts).

### Denial at the helper request boundary

**Observed in Pi 1.1.0 source:** Direct `onPayload` is distinct from the global extension event. Built-in Anthropic and OpenAI completions adapters await it before their model HTTP request. A thrown error reaches their request failure handling rather than continuing with the old payload. The SDK's global event bridge discards the callback's model argument and catches extension errors inside event dispatch. Direct registry helper calls must explicitly provide their own callbacks; they do not automatically reproduce the SDK event bridge. [Anthropic adapter](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/src/api/anthropic-messages.ts), [OpenAI completions adapter](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/src/api/openai-completions.ts), [SDK bridge](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/sdk.ts).

**Observed in Pi 1.1.0 runtime with conforming fake providers:** A per-call `onPayload` denial produced an error result without simulated dispatch. A rejecting per-call `transformHeaders` stopped entry into the provider stream function. By comparison, exceptions from both global extension hooks were reported and swallowed; dispatch returned the unchanged payload or headers. These establish the tested local boundaries, not enforcement against arbitrary extension code.

A supported observer can accept different resolved models on consecutive requests when each falls within the same authorized policy. Validate the actual model, provider, relevant endpoint, required account identity, and request capacity on each request. A route change within that policy need not invalidate authorization. Invalidate pending work when the package-owned authorization or configuration policy changes; Pi does not provide the required generation number. If a provider-specific identity check cannot be completed, stop before sending the observer evidence and report degradation.

The callback only guards the final model request it observes. Authentication refresh can happen earlier. A virtual router can itself send the transcript to a classifier or another service before choosing the final model. Authorizing only the returned physical model does not authorize that earlier data transfer. The router and any helper calls it makes need their own established authorization policy.

### Account identity and concrete model pinning

**Observed in Pi 1.1.0 source:** The generic non-secret `CredentialInfo` has provider ID and credential type, not a stable account identifier. `ModelAuth` has API key, headers, and base URL; credential environment can include provider-specific account configuration. Some accounts can be identified from provider headers or credential metadata, but the generic APIs do not normalize this. Request options can also affect endpoint selection through provider environment. A model's provider and ID alone do not establish the billed account or final network destination. [Auth types](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/src/auth/types.ts), [runtime auth assembly](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/model-runtime.ts).

**Observed in Pi 1.1.0 runtime:** Passing a concrete physical model to `registry.streamSimple()` bypassed the virtual router. Passing an explicitly resolved API key preserved that key after the fixture re-registered the provider with another key. This establishes a possible explicit-credential path for that fixture. It does not show that a model object freezes the provider implementation, environment, endpoint, account, or credentials generally. The registry still looks up its provider and resolves request auth. Fully fixed dispatch needs a controlled provider integration, explicit resolved options where supported, and boundary validation. Secrets must not enter status text or persisted evidence.

## Nonmodal degradation alerts

**Observed in Pi 1.1.0 source:** The public UI methods have mode-specific behavior:

| Mode  | Unsolicited alert                                                                             | Persistent status                                                                                            | Limit                                                                                                                                    |
| ----- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| TUI   | `ctx.ui.notify(message, 'warning')` renders a warning without a confirmation dialog           | `ctx.ui.setStatus(key, text)` updates the footer; `setWidget` can add detail                                 | UI status is not a durable record.                                                                                                       |
| RPC   | `ctx.ui.notify` emits `extension_ui_request` with `method: 'notify'`; no response is required | `setStatus` emits its corresponding fire-and-forget request; string-array widgets are supported              | The client must render notifications; emission does not prove a human saw them.                                                          |
| Print | Write a concise diagnostic to stderr                                                          | Status must be available through a package-owned report or durable state if needed                           | `ctx.ui.notify`, `setStatus`, and widgets are no-ops.                                                                                    |
| JSON  | Write diagnostics to stderr, preserving JSONL stdout                                          | If machine-readable persisted state is needed, `pi.appendEntry()` produces a standard `entry_appended` event | There is no general ephemeral extension-notification event in this mode. A custom entry is a storage decision, not a substitute UI call. |

Sources: [TUI notification adapter](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/modes/interactive/interactive-mode.ts), [RPC UI implementation](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/modes/rpc/rpc-mode.ts), [print/JSON binding](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/modes/print-mode.ts), [default no-op UI](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/extensions/runner.ts), [JSON event contract](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/docs/json.md).

A practical alert policy emits one warning when a degradation reason begins or materially changes, updates status while it persists, and clears status on recovery. This is a package policy recommendation; Pi does not supply automatic deduplication or acknowledge notification receipt.

## Alternatives and recommendation

| Approach                                                                | Feasibility                                                                                        | Decision consequence                                                                                                        |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Explicit authorized target policy with per-call observer validation     | Supported for cooperating routers/providers whose endpoint and account identity can be established | Recommended when preserving legitimate dynamic observer routing. Do not require the next route to equal the previous route. |
| Concrete observer provider/model with controlled credential integration | Public concrete model dispatch, auth resolution, and provider methods are available                | Narrower and easier to verify; model pinning alone does not pin account or endpoint.                                        |
| Trust any virtual selection's advertised limits and selected identity   | No enforced cross-route capacity or account guarantee                                              | Insufficient for the stated capacity and destination contracts.                                                             |
| Treat global provider extension hooks as authorization vetoes           | Handler errors are swallowed and resolved identity is incomplete                                   | Insufficient for denial; use the observer's own request callbacks or a controlled dispatch adapter.                         |

Omit the file supplement when virtual acting-request capacity cannot be bounded. A per-call observer callback does not expose the acting request's route to a context handler. For observers, define authorization as membership in an explicit destination/account policy and validate each actual request through supported provider boundaries. Support dynamic virtual routing only where those checks and any router-internal inference are covered. Where they are not, require a concrete supported integration or report the observer as unavailable. Use mode-appropriate nonmodal alerts rather than asking for confirmation on each update.

## Probe and gaps

**Observed in the bounded probe:** Executed a temporary script against installed Pi 1.1.0 packages outside the repository. The successful run tested alternating virtual routes with identical catalog data, per-call payload and header denial, concrete model dispatch, explicit fixture-credential preservation, and swallowed global-hook exceptions. It completed three simulated dispatches; denied calls did not simulate sending. Global fetch and socket operations were configured to throw. It did not start an agent session, call a real model, or make a network request.

Built-in adapter callback ordering, account metadata, and TUI/RPC/print/JSON behavior were source-inspected, not runtime-tested here. OAuth rotation, ambient cloud credentials, custom provider nonconformance, HTTP redirects, WebSocket transports, proxy/gateway routing, concurrent policy replacement, and router-internal classifier calls remain untested. A production claim needs provider-specific offline transport and credential fixtures plus UI-mode delivery fixtures. No general account-identity or route-generation guarantee can be obtained by adding those tests alone; it needs an explicit supported integration contract.
