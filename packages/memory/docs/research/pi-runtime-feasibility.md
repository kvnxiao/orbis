# Pi request capacity and checkpoint preparation

Pi 1.1.0 supplies the public inputs needed to preserve its prepared compaction cut and process the complete discarded history and split-turn prefix. It also supports request-local file supplements. It does not expose a universally authoritative final request size, current routed model, or output allocation to a context handler. Preserve the supplement contract as bounded estimation with an explicit omission path, and preserve checkpoint preparation with whole-checkpoint fallback when coverage or a defensible capacity bound cannot be established. Do not promise that a handler's estimate proves the eventual provider request fits.

## Decision informed

The memory package replaces Pi's summary only when its maintained state accounts for the prepared evidence and its complete rendering fits a documented budget. When a native checkpoint is used, it adds cumulative file inventory to the acting request without changing stored checkpoint text. These operations need separate budget decisions: a custom checkpoint must fit alongside the retained conversation, while a supplement must fit alongside the entire existing native checkpoint. This research evaluates the public host capabilities behind those decisions; it does not evaluate model-generated summary quality or a memory implementation.

## Public request inputs

A forced prompt replaces the normal system prompt; forced-prompt projection is the host transformation that applies it. Loadout hooks control which tools and declarations are available for a request. A virtual model routes a selection to a concrete model, which can have different capacity limits.

**Observed in Pi 1.1.0 source and scripted runtime:** The ordinary `context` event excludes system messages. Pi restores prompt and tool state after those handlers. `context_with_system` runs afterward and supplies the full transcript, including system messages and their tool declarations. Its handlers execute sequentially, so an earlier handler cannot see changes a later handler will make. Returned messages are request-local; the hook operates on a structured clone rather than rewriting persisted entries. [Extension contracts and dispatch](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/extensions/runner.ts).

**Observed in Pi 1.1.0 source:** `convertToLlm()` adds compaction and branch-summary wrapper text, converts shell messages, and excludes shell executions marked `excludeFromContext`. SDK conversion can subsequently replace images with disabled-image placeholders. Provider adapters then normalize messages, schemas, and protocol fields. An estimate over raw message bodies alone omits request material or counts material that will be removed. [Message conversion](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/messages.ts), [SDK conversion](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/sdk.ts).

**Observed in Pi 1.1.0 source:** Pi installs hidden-declaration filtering and forced-prompt projection around the existing SDK context transformation. These run after both extension context phases and before LLM message conversion. A forced prompt collapses system messages into a leading prompt with current tools. Consequently, adding both the full hook's system messages and `getSystemPrompt()` to a sum double-counts prompt content; treating either view as universally final is also incorrect. A supported estimator must model the applicable projection, establish a conservative bound over known alternatives, or decline. [Host projection order](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/agent-session.ts).

## Estimation and output reserve

**Observed in Pi 1.1.0 source and scripted runtime:** The coding-agent root exports `estimateTokens()` and `convertToLlm()`. Its per-message estimator uses characters divided by four and fixed image estimates. It does not add the compaction wrapper when applied directly to a `compactionSummary`. A fixture with a 100-character summary estimated 25 tokens before conversion and 52 after conversion. Pi AI's separately exported `@earendil-works/pi-ai/utils/estimate` estimated the converted fixture as 60 tokens, using a 3.5-character divisor. These are heuristic outcomes, not measured tokenizer counts or proof of an upper bound. The coding-agent source's `estimateContextTokens()`, `estimateProjectedContextTokens()`, and `prepareCompaction()` are not exported from its package root; their existence in source does not authorize deep imports. [Coding-agent exports](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/index.ts), [coding-agent estimator](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/compaction/compaction.ts), [Pi AI estimator](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/src/utils/estimate.ts).

**Observed in Pi 1.1.0 source and a direct helper probe:** Built-in simple request options normally start from the requested cap or `model.maxTokens`, then clamp against estimated context and a 4,096-token safety allowance, with a minimum cap of one. A fixture whose estimated context already exhausted the available window returned a cap of one. This calculation does not reject an oversized input or prove provider acceptance. Provider-specific thinking behavior and custom providers can differ. Compaction `reserveTokens` controls its threshold and influences summary generation; it is not the acting request's final `max_tokens` value. [Simple request options](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/src/api/simple-options.ts), [compaction settings](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/settings-manager.ts).

A supplement policy can reserve a documented output allowance without knowing the exact later cap, provided that allowance bounds the supported request behavior. The same policy needs a defined uncertainty margin for wrappers, tokenization, and known transformations. If it cannot bound the physical model or later additions, it cannot claim usable capacity merely because the current transcript is small. Counting every registered tool or taking the current usage total does not repair this gap.

### Virtual routing

**Observed in Pi 1.1.0 scripted runtime:** A selected virtual model had `contextWindow: 100000` and `maxTokens: 8192`. During its request, `ctx.getContextUsage()` returned `contextWindow: 12000` and `tokens: null`, reflecting earlier physical-model state. The scripted provider received a different physical model with `contextWindow: 4096`. This reproduces a concrete case in which neither public context value identifies the current request's capacity.

**Observed in Pi 1.1.0 source:** Agent request preparation resolves a virtual model before context transformation, but the selected model remains in agent state. `ctx.model` reads that selection. The usage window comes from the latest successful physical response when available. The hook does not receive the newly resolved route. Calling a router separately is not proof of the route already chosen for the acting request and can differ by conversation, retry reason, or state. [Request routing and limits](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/agent-session.ts), [virtual-model contract](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/virtual-models.ts).

For a virtual model, a cooperating router could supply a trusted request limit, or an integration could establish a bound covering every allowed route. Without such an established integration, omission is the supported result. A previous request's physical model is not sufficient evidence.

## Prepared checkpoint and split-turn evidence

A split turn divides one user request and its assistant/tool continuation at the compaction boundary. The discarded earlier portion is the turn prefix; the later portion stays in recent history. Protected strings are exact identifiers or source wording selected for verbatim preservation because paraphrase could weaken their meaning.

**Observed in Pi 1.1.0 source and scripted runtime:** `session_before_compact` provides `messagesToSummarize`, `turnPrefixMessages`, `previousSummary`, `isSplitTurn`, `firstKeptEntryId`, `tokensBefore`, settings, file operations, branch entries, instructions, retry intent, and cancellation. These inputs are sufficient to distinguish earlier history from the discarded prefix of an unfinished turn and preserve the host-selected cut. A model-free custom-compaction fixture received an edited user message in the turn prefix and preserved the exact retained assistant entry. A second custom compaction received the first custom checkpoint as `previousSummary`. [Preparation](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/compaction/compaction.ts), [hook declaration](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/extensions/types.ts).

**Observed in Pi 1.1.0 source and scripted runtime:** Prepared summary inputs exclude the retained suffix. Public `buildSessionProjection(event.branchEntries)` exposes effective messages and their source entries, allowing the retained suffix to be derived from `firstKeptEntryId` for capacity accounting. The fixture found the retained assistant entry in that projection. Request-local content added by a context handler was absent from subsequent preparation. Persistent context edits affected prepared text. Therefore, prepared evidence and the final acting-request transcript are related but distinct domains.

**Observed in Pi 1.1.0 source:** Native split compaction may produce an earlier-history summary and a separate turn-prefix summary. The history call receives custom instructions and the previous summary; the prefix call does not. A custom implementation can apply its instructions to both prepared domains because the hook exposes them together. It must still distinguish discarded prefix evidence from retained suffix capacity. The hook has no supported preparation-replacement return value. [Native split compaction](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/compaction/compaction.ts).

This supports preserving the checkpoint preparation contract. Structural inclusion, exact obligation text, protected strings, file inventory, and size under the chosen estimator are checkable by code. Whether a generated presentation preserves every necessary meaning remains an evaluation question. A helper request also has its own system prompt, structured-output instructions or schema, input state, prepared text, and output budget; capacity of the acting request does not establish that the helper input fits.

## Alternatives

| Approach                                                           | Public feasibility                                                                                  | Consequence                                                                                                                |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Estimate the supported request and omit when limits are unresolved | Public message, prompt, tool, model, and projection APIs supply the inputs for known configurations | Preserves useful supplements while making unsupported routing and unbounded later transforms explicit. Recommended.        |
| Claim every final provider request fits based on the context hook  | The hook precedes later handlers, host projections, conversion, and provider payload transforms     | Unsupported by Pi 1.1.0; the runtime fixtures give counterexamples to complete visibility.                                 |
| Implement provider-specific final-payload sizing                   | Payload hook exists, but payload is untyped and subsequent handlers can replace it                  | Requires separately scoped provider and ordering contracts; does not follow from the current portable supplement contract. |
| Omit supplements universally                                       | Always feasible                                                                                     | Discards useful public capability even for fixed models and controlled transformations.                                    |

## Recommendation

Preserve the split-turn and complete prepared-evidence requirements. Preserve file supplements as deterministic selection against a documented estimated capacity, including the complete native checkpoint and converted wrappers. Require explicit omission with a status reason when current model limits, output reserve, or later request changes cannot be bounded. Apply the same distinction between estimates and provider guarantees to complete custom-checkpoint fitting. Keep whole-checkpoint native fallback when custom preparation cannot establish eligibility. The existing omission rule permits this behavior; an amendment should make its unsupported conditions and estimation scope concrete rather than promising final-provider precision.

## Executed probes and remaining gaps

**Observed in the isolated Pi 1.1.0 probe:** Installed the coding-agent, agent-core, and AI packages at exactly 1.1.0 with `pnpm add --ignore-scripts --save-exact`; resolved Pi dependencies were also 1.1.0. Executed the isolated probe with Node.js 26.10.0. The final successful run made three scripted in-process provider calls and completed two custom manual compactions. It used in-memory session and settings managers, an in-memory credential implementation, an explicit resource-loader object, and explicit extension objects. Global fetch and socket connection operations were configured to throw; no real model or live agent process ran. The fake provider invoked the public payload callback and returned fixed assistant responses. The final scripted assertions passed. The probe did not run a memory package implementation.

Actual helper inference, provider tokenizers, provider rejection thresholds, images, tool configurations with hidden declarations, SDK custom stream overrides, overflow retries, cancellation races, and native generated fallback were not runtime-tested. Hidden-declaration and image conversion findings are source-inspected. The output-clamping check invoked an exported helper directly; it was not a built-in provider network request. Settling token error margins needs tokenizer or offline provider-payload fixtures for each supported configuration. Settling semantic preservation needs separate quality evaluation.
